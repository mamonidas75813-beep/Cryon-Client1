# CRYON CLIENT — SignPath Foundation preparation

**Not yet approved, signed, or production-ready.** Existing app UI and runtime behavior are unchanged. This is a proposed candidate-signing workflow, not a complete signed-update migration.

## Before applying

1. Confirm you own the project and have rights to all source, assets, branding and dependencies. Preserve the MIT license; audit all components, bundled code and licenses against https://signpath.org/terms. Investigate the existing `CrackAuth` calls in `src/main.js`: offline test identity behavior must not bypass Minecraft purchase/entitlement or server authentication. Review and correct any noncompliant behavior before applying. Disclose actual behavior; do not hide it or rename it to evade review. Complete a dependency/security audit (including Java, mods and Playit downloads and updater). This ZIP is not a completed whole-project security audit.
2. Keep two repositories if desired: public source (suggested `mamonidas75813-beep/CRYON-PRIVATE`, made public only after secret/history review, or a new public name) and public downloads (`mamonidas75813-beep/CRYON-RELEASES`). Check all Git history and rotate any previously exposed credentials. Confirm repository ownership and names; no GitHub changes have been made by this package. Never commit PFX, PAT, API token, account files or private data. Keep source, build scripts and workflows in the public repository root.
3. In a clean Node.js 24 checkout, run `npm install --package-lock-only --ignore-scripts`, review the resolved versions/provenance and commit `package-lock.json`. Run `npm ci --include=dev`, `npm run check`, `npm test`, and `npm audit`. Resolve failures and commit reviewed lockfile changes. The lockfile could not be generated in the preparation environment (npm registry DNS failure). Do not create a fake lockfile. CI intentionally fails without one.
4. Confirm named roles in CODE_SIGNING_POLICY.md, review PRIVACY.md, enable private vulnerability reporting, protect main/version tags and enable MFA. Add the code signing policy link to the public source README, public downloads README and release notes. `release-repo-docs/README.md` is a starter: replace its source URL with the verified public repository URL before copying it into the downloads repository. Confirm third-party privacy and licenses.
5. Run Actions → SignPath Windows candidate on main with `request_signing=false`. Inspect the unsigned installer artifact, test install/launch/uninstall on Windows, and make a real, clearly labeled existing release only after security, licensing and distribution review. Never claim it is signed. Show legitimate maintenance history and verifiable usage/reputation. The Foundation requires existing releases and reviews reputation; no minimum star count or approval is promised.
6. Apply at https://signpath.org/apply (or use Apply on https://signpath.org/). Provide actual public source and release URLs, MIT license, policy URL, real maintainers and truthful project/reputation information. See SIGNPATH_APPLICATION.md. Do not invent downloads, stars, or approval.

## After approval: candidate workflow only

- Follow the Foundation onboarding and https://docs.signpath.io/trusted-build-systems/github. Authorize the official GitHub integration and restrict it to the approved public source. In SignPath create the project, trusted build connection/pipeline policy (GitHub-hosted runners, reviewed workflow and protected stable tags) and a release policy with required human approval. Review `signpath/installer-artifact.xml` with SignPath, validate against the live schema, and confirm PE product-name/version restrictions. It targets just the exact NSIS installer inside the GitHub artifact ZIP; no third-party files are requested for signing. If SignPath requires different coverage or rejects metadata, stop and revise with them.
- Configure GitHub Settings → Environments → `signpath-release`; restrict deployment to protected tags and add required reviewers where available. Store `SIGNPATH_API_TOKEN` as an environment secret scoped to submission. Configure environment variables `SIGNPATH_ORGANIZATION_ID`, `SIGNPATH_PROJECT_SLUG`, `SIGNPATH_SIGNING_POLICY_SLUG`, `SIGNPATH_ARTIFACT_CONFIGURATION_SLUG` exactly as assigned. No PFX download or private signing key is needed. Do not grant signing approval to automation.
- Use a new release version matching `package.json` and a protected `vX.Y.Z` tag, and manually dispatch SignPath Windows candidate on that tag with `request_signing=true`. Review each signing request in the SignPath portal. The workflow verifies the returned installer signature, publisher and timestamp, then uploads a candidate with checksum. It does NOT upload a GitHub release or publish auto-update metadata.
- Validate the candidate on a clean Windows VM. Before a production signing switch, design and validate signing of the embedded launcher and uninstaller (e.g. staged packaging with SignPath-approved signing of project-owned PE files), portable output, and installer. This draft only signs the outer setup EXE. Do not present it as fully signed installed software.
- Important updater warning: signing changes bytes. Existing electron-builder `latest.yml`, SHA-512, blockmap and unsigned checksums are not valid for a post-build signed installer. Do not publish them. Finalize packaging and signing order, regenerate final update metadata/blockmap with supported electron-builder tooling, configure trusted publisher verification for SignPath, and test upgrade from the previous release, including negative tampering tests. Until then keep SignPath output as a candidate only. Do not enable the old PFX workflow as a workaround for Foundation rules.

## Legacy path

The original PFX release workflow remains available only as explicit manual opt-in on a matching version tag, for separately authorized legacy signing. It is not the Foundation workflow. Tag pushes no longer trigger release publication automatically. No runtime updates or policies are silently changed by this preparation.
